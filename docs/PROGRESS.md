# 진행 내역 체크리스트 — sbmig (flow-v2)

이 파일은 회사에 배포되는 sbmig(브랜치 `flow-v2`)가 지금까지 무엇을 하게 되었는지를 한 줄씩 적은 체크리스트다. 2026-11-11 기준의
스냅샷이며, `- [x]` 는 만들어져 있는 것, `- [ ]` 는 아직 안 된 것 또는 회사의 답을 기다리는 것이다. 라운드별 자세한 내용(파일, 테스트,
검증 수치)은 `docs/PLAN.md`, 계약은 `docs/INTERFACES.md`, 현업 요청과 v2 결정은 `docs/v2/PLAN-v2.md` 에 있다. v1 시절 기록은 git 태그
`company-v1` 에만 남긴다.

## 1. 이관 흐름 (접수 · 분석 · 계획 · 자동 변환 · 구조 정리 · 구조 검토 · 빌드와 수정 · 마무리)

**접수**
- [x] Maven 프로젝트 ZIP / 폴더를 받아 처음 상태를 git 커밋으로 남기고, JDK 21 · Maven 준비를 미리 검사한다(preflight)
- [x] Ant 프로젝트(build.xml 만 있고 pom.xml 이 없음)는 build.xml 을 읽어 pom.xml 을 만들어 준 뒤 Maven 프로젝트처럼 이관한다 (v2.1j)
- [x] Ant 의 jar 좌표는 jar 안 정보 → 이름 표 → 저장소 sha1 조회 순으로 찾고, 못 찾은 jar 는 `system` 범위로 두고 인수인계에 설치 명령을 적는다
- [x] Gradle 프로젝트와 pom.xml · build.xml 이 모두 없는 트리는 받지 않는다(종료 코드 3), 그런 트리는 `sbmig inventory` 로 설명만 한다
- [x] 루트 pom 이 없는 트리(형제 pom, `APP/pom.xml` 이 `../DEV` 를 묶는 회사 모양)에는 루트 집계 pom 을 만들어 준다 (v2.1k)
- [x] 집계 pom 이 하나뿐이면 그 옆의 묶이지 않은 pom 이 있어도 그것을 루트로 삼고, 빠진 pom 은 인수인계에 이름을 적는다
- [x] 리액터에 두 번 들어간 모듈은 접수 때 한 번으로 줄인다 (`reactor-duplicate-removed`)
- [x] IDE 출력 · 백업 폴더에 통째로 복사된 모듈(`boot/bin/` 같은 떠도는 pom 복사본)은 모듈로 보지 않고 모든 검사에서 뺀다 (v2.1z-h)
- [x] 회사 parent 체인의 빌드 확장(wagon 등)을 미리 검사하고, 배포용 확장은 첫 Maven 호출 전에 뺀다

**분석**
- [x] 프로젝트 유형(순수 Java · Spring 4/5 · Boot 2/3 · Tomcat 서블릿 · MSA)과 라이브러리, EOL 라이브러리 권고를 찾는다
- [x] 모듈이 소스를 하나도 컴파일하지 않는데 소스는 다른 폴더에 있는 "속 빈 리액터"는 성공으로 치지 않는다(종료 코드 2, 인수인계 첫 줄) (v2.1z-c)
- [x] Oracle ADF(JDeveloper) 프로젝트는 증거 4종 중 2종 이상이면 "ADF 프로젝트라 변환이 불가능합니다" 로 분석에서 멈춘다, 1종이면 메모만 (v2.1z-d)
- [x] 어떤 pom 도 선언하지 않은 트리 안의 jar(WEB-INF/lib 의 벤더 암호화 · SSO jar)를 내용으로 찾아 목록으로 남긴다 (v2.1z-i)
- [x] 필터링되는 리소스 안의 바이너리 파일(글꼴, `.dmdb` 등)을 확장자가 아니라 내용으로 찾는다

**계획과 자동 변환**
- [x] OpenRewrite 를 한 번만 돌린다: Java 21, javax → jakarta(필요할 때), Boot 프로젝트에는 Boot 4.0 + 4.1 속성 레시피
- [x] Spring Framework 7 레시피는 레거시 Spring 프로젝트 전부에, Spring Security 6 → 7 체인은 Security 를 쓰는 프로젝트에만 돌린다
- [x] Spring Batch 6 · Hibernate 7 레시피는 쓰는 경우만, 서블릿 jakarta 10 레시피는 Tomcat 서블릿 프로젝트에 돌린다
- [x] 레시피 목록은 `knowledge/recipes/catalog.yml` 한 곳에만 있고 `sbmig recipes check` 가 어긋남을 잡는다
- [x] 구조 정리를 마치기 전에는 빌드를 돌리지 않는다(반쯤 바뀐 트리에서 빌드하지 않음) (v2.1o)

**구조 정리 (회사 레이아웃, 3절의 규칙)**
- [x] 비-Boot 프로젝트는 `{name}-boot` / `{name}-back` / (웹 자원이 있으면) `{name}-front` 모듈로 나누고, Boot 프로젝트는 폴더를 그대로 두고 pom 만 바꾼다
- [x] 동봉 jar 는 첫 빌드 전에 연결한다: 저장소에 좌표가 있으면 일반 의존성, 없으면 `<module>/lib/` + `system` 범위 + Nexus 게시 요청 (v2.1z-j)
- [x] 목표 체인이 이미 관리하는 옛 jar(예: WEB-INF/lib 의 spring-webmvc 4.x), 컨테이너 API, 아무도 쓰지 않는 jar 는 연결하지 않고 이름만 적는다
- [x] 레거시 Spring 컨텍스트(web.xml 필터, JNDI, 멀티파트, 정적 자원, 프로필 파일 등 14가지)를 Boot 설정으로 옮기는 규칙을 스위치로 둔다 (v2.1x)
- [x] 모든 정적 자원이 front 모듈에 닿고, WEB-INF 아래 설정 아닌 파일은 경로를 지킨다

**구조 검토**
- [x] 구조 정리 뒤 LLM 이 pom · 의존성 · 모듈 · 소스 인코딩 · 필터링되는 바이너리를 회사 규칙과 대조한다
- [x] 심각한 문제만 고치고(편집 답, 커밋 `review: …`), 경고는 보고서와 오류 목록에만 적는다
- [x] 검토가 고친 결과가 불변조건(예: 떠도는 복사본을 모듈로 등록)을 깨면 되돌리고 LLM 에게 이유를 말해 다시 묻는다

**빌드와 수정 · 마무리**
- [x] `mvn clean package -Dmaven.test.skip=true` 로 판정하고, 실패하면 2절의 수정 루프를 돈다
- [x] 어떤 실행도 마지막 빌드 시도와 남은 오류 목록 없이 끝나지 않는다(빌드 게이트)
- [x] 보고서(report.md, 인수인계가 맨 앞), `errors.md` / `errors.jsonl`, 운영자가 옮겨 적는 `SBMIG-RESULT …` 한 줄을 남긴다
- [x] Windows 에서 `target/` 파일 잠금으로 빌드가 실패하면 LLM 에 묻지 않고 기다렸다 다시 빌드한다 (v2.1r)
- [x] 부모 pom 에서 물려받은 pom 문제는 자식이 아니라 부모 pom 을 가리킨다 (v2.1z-y)
- [x] 실행마다 `sbmig.log`(DEBUG)와 저널을 남기고, LLM 요청 · 응답 기록은 켤 때만 남긴다

## 2. 빌드 오류 수정 루프와 지식베이스

- [x] 빌드 오류를 케이스(L2 서명)별로 묶고, 원인 쪽(pom · 의존성)부터 고치며 같은 파일을 건드린 케이스는 다음 빌드까지 기다린다
- [x] 사다리: 저장된 가장 좋은 스크립트 재사용(LLM 없음) → 이번 실행의 스크립트 보강(LLM) → 보강을 다 쓰면 새 스크립트(LLM)
- [x] 한도는 넉넉히: 케이스당 LLM 20회, 그중 보강 15회, 넘으면 BLOCKED `repeated_failure` (v2.1z)
- [x] 매 시도를 커밋하고 다시 빌드해 점수를 매긴다(좋아짐 · 일부 · 변화 없음 · 나빠짐 → 되돌림), 좋아지지 않은 시도는 다음 시도 전에 되돌린다
- [x] pom 수정이 다음 빌드 단계의 오류를 드러낸 것은 나빠진 것으로 치지 않는다 (v2.1z-z)
- [x] 수정 스크립트는 제한 API 로 별도 프로세스(`python -I`)에서, 프로젝트 폴더 안에서만, 시간 제한과 함께 돈다
- [x] 스크립트는 케이스별로 `kb-v2/cases/<case_id>/fix_v<N>.py` 에 저장되고 성공 · 실패 · 프로젝트 · 계보 · 실패 이유가 `case.json` 에 쌓인다
- [x] 수정 전 · 후 코드 조각(as-is / to-be)과 시도 없이 해결된 오류의 해결자를 기록한다 (v2.1e, v2.1f)
- [x] 두 번째 실행에서 다른 결과를 내는 스크립트는 다시 쓰지 않는다
- [x] 케이스 키에서 프로젝트의 모듈 이름을 `<module>` 로 가려 다른 프로젝트도 같은 케이스를 찾는다 (v2.1z)
- [x] LLM 없이 먼저 시도: 버전 없는 의존성 채우기(`sbmig-version`) (v2.1l)
- [x] LLM 없이 먼저 시도: 바이너리 리소스 필터링 오류(`sbmig-resources`) (v2.1m)
- [x] LLM 없이 먼저 시도: 저장소에서 찾은 jakarta 빌드로 바꾸기(`sbmig-jakarta`) (v2.1z-e)
- [x] LLM 없이 먼저 시도: 필요한 동봉 jar 연결(`sbmig-bundled`) (v2.1z-i)
- [x] 리액터 중복 · 파일 잠금 오류는 LLM 에 보내지 않는다
- [x] LLM 이 거절한 케이스는 1회 뒤 BLOCKED(`needs_owner`), 다만 sbmig 가 대체 방법을 아는 라이브러리(Spring Mobile 등)는 거절을 받지 않고 다시 묻는다 (v2.1z-aa)
- [x] EOL 라이브러리를 프로젝트 코드로 대체하는 일은 스크립트가 아니라 직접 편집 답으로 받고 4회로 제한한다
- [x] A↔B 를 오가는 진동은 `loop.oscillation_limit` 로 막는다
- [x] javax 라이브러리는 sbmig 가 직접 저장소 집합(설정 미러, Central 등)에서 jakarta 빌드를 찾고, `sbmig repo-probe` 로 무엇을 물었는지 보여 준다
- [x] 여러 빌드 파드가 한 KB 폴더에 동시에 써도 깨지지 않게 잠금과 "없을 때만 만들기"로 보강했다
- [x] 실행 사이에 KB 를 보는 명령: `sbmig kb cases list` / `show`, `sbmig kb reindex`
- [ ] 서명 규칙을 바꾸면 저장 케이스가 고아가 되는 문제 — `kb reindex --resign` 제안만 있음
- [ ] 흔한 메서드 이름을 공유하는 다른 문제가 한 케이스로 합쳐지는 문제 — 위의 것 다음에만 고칠 수 있음

## 3. 회사 규칙

- [x] 루트 pom 은 사내 `base-parent` 를 상속하는 집계 pom, boot 모듈은 `boot-jar`, 나머지 모듈은 `comp-jar` 를 부모로 둔다
- [x] 필수 사내 아티팩트 2개는 모든 루트 pom 에 선언한다
- [x] 선택 사내 아티팩트 8개는 이미 쓰는 경우만 맞추고, 트리거 의존성(예: hibernate-core)이 있으면 회사 아티팩트로 바꿔 넣는다 (v2.1n)
- [x] JSP 가 있으면 boot 모듈은 실행 가능한 WAR(`java -jar` 로 내장 Tomcat), 아니면 실행 가능한 jar 다
- [x] MSA 는 서비스마다 같은 부모 · 필수 · 선택 규칙, 폴더 구조는 그대로(pom 만)
- [x] 회사 좌표는 설정 YAML 에만 있고 코드에는 없다(예제는 자리표시자)
- [x] 버전은 추측하지 않는다: as-is 부모가 관리하던 버전은 as-is 유효 pom 에서 옮겨 고정, 모르면 비워 둔다 (v2.1l)
- [x] 회사 parent 체인의 관리 버전 · 속성 이름은 그 pom 들을 직접 읽어 얻는다(Boot BOM 포함) (v2.1p)
- [x] 체인이 관리하지 않는 버전은 목표 Boot BOM 을 따르고, 체인에 Boot BOM 이 없으면 경고한다 (v2.1s)
- [x] BOM import 와 사내 버전은 체인의 속성(`${spring-boot.version}` 등)을 가리킨다 (v2.1t)
- [x] LLM 은 스스로 메이저 버전을 올리거나 라이브러리를 바꾸지 않는다, 메이저 변경은 막지 않되 운영자 확인 항목으로 적는다 (v2.1d)
- [x] 체인을 덮어쓰는 as-is 버전 속성, 참조 없는 버전 속성, Boot BOM 을 가리는 as-is 관리 항목을 지운다 (v2.1z-k, v2.1z-l)
- [x] 목표 라인에 없는 옛 Spring 아티팩트(spring-dao 등)는 버전을 박지 않고 지운다
- [x] JSP · 태그 파일 안의 javax EE 이름을 jakarta 로 바꾼다(태그 라이브러리 URI 는 그대로) (v2.1h)
- [x] 필터링되는 리소스의 바이너리 확장자를 maven-resources-plugin `nonFilteredFileExtensions` 에 적는다 (v2.1m)
- [x] EUC-KR / MS949 pom 을 읽고 같은 인코딩으로 저장한다
- [x] EOL 라이브러리는 막지 않고 LLM 힌트와 인수인계로만 안내한다
- [x] 테스트는 컴파일하지 않는다(`-Dmaven.test.skip=true`), 인수인계에 담당 팀 후속 과제로 적는다
- [ ] MSA 안의 비-Boot WAR 서비스 — 지금은 boot 부모만, 실제 프로젝트를 보고 결정
- [ ] base-parent 에 Boot BOM import 추가 — 회사(부모 소유자)의 결정

## 4. LLM 게이트웨이

- [x] 기본 provider `company`: `.env` 의 주소 · 키 · 모델로 requests 한 번 호출(LangChain 없음), 키는 환경 변수에서만
- [x] 사내 GPT agent 게이트웨이(`llm.gateway: agent`): asset id, 역할 이름(`build_error_fixer` / `escalation_fixer`) (v2.1z-m)
- [x] 앱 토큰 → 접근 토큰 교환, 만료 5분 전 갱신, 401 뒤 한 번 더 받기
- [x] 게이트웨이가 돌려준 세션 id 를 받아 두고, 이어 갈 때만 다시 보낸다(`thread_id` 는 보내지 않음) (v2.1z-o)
- [x] 케이스 스레드(`llm.case_thread`, 기본 꺼짐): 같은 케이스의 보강은 같은 세션에 바뀐 부분만 보낸다 (v2.1z-p)
- [x] 모델이 바뀌는 요청(세 번째 요청의 상위 모델 등)은 새 세션을 연다 — 열린 세션은 모델을 못 바꾼다 (v2.1z-x)
- [x] 게이트웨이가 바쁠 때(429 / 5xx + Retry-After)는 실패하지 않고 줄 서서 기다린다(`llm.busy_wait_seconds`)
- [x] `sbmig llm-probe` 로 실제 요청 · 프록시 · 응답 · 토큰 교환을 보여 준다
- [x] 회사 LLM 이 끼어들 자리(어댑터 `llm.plugin`, `fix.plugin`)를 유지한다
- [ ] 케이스 스레드를 켤지 — 세션의 이전 턴 과금이 문서에 없어 회사 실행의 수치를 보고 결정
