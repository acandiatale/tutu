# 진행 내역 체크리스트 — sbmig (flow-v2)

이 파일은 회사에 배포되는 sbmig(브랜치 `flow-v2`)가 지금까지 무엇을 하게 되었는지를 한 줄씩 적은 체크리스트다. 2026-11-12 기준의
스냅샷이며, `- [x]` 는 만들어져 있는 것, `- [ ]` 는 아직 안 된 것 또는 회사의 답을 기다리는 것이다. 라운드별 자세한 내용(파일, 테스트,
검증 수치)은 `docs/PLAN.md`, 계약은 `docs/INTERFACES.md`, 현업 요청과 v2 결정은 `docs/v2/PLAN-v2.md` 에 있다. v1 시절 기록은 git 태그
`company-v1` 에만 남긴다.

## 1. 이관 흐름 (접수 · 분석 · 계획 · 자동 변환 · 구조 정리 · 구조 검토 · 빌드와 수정 · 마무리)

**접수**

- [x] Ant 프로젝트(build.xml 만 있고 pom.xml 이 없음)는 받지 않는다: 접수에서 멈추고(종료 코드 3, `unsupported-build-tool:ant`) 안내 문구 "Maven 변환 후 신청 부탁드립니다." 를 보여 준다(`intake.ant_message`) — 회사 결정

- [x] IDE 출력 · 백업 폴더에 통째로 복사된 모듈(`boot/bin/` 같은 떠도는 pom 복사본)은 모듈로 보지 않고 모든 검사에서 뺀다 (v2.1z-h)
- [x] 회사 parent 체인의 빌드 확장(wagon 등)을 미리 검사하고, 배포용 확장은 첫 Maven 호출 전에 뺀다

- [x] Hystrix 를 쓰는 프로젝트는 사내 레시피로 Resilience4j 로 바꾼다(`@HystrixCommand` → `@CircuitBreaker`, starter 교체). 버전은 적지 않고 Spring Cloud BOM 이나 재구성 규칙이 정한다. 레시피가 못 바꾸는 코드(`HystrixCommand` 상속 등)는 수정 루프가 옮긴다. Springfox 와 `spring-cloud-starter-sleuth` 는 Boot 4 상위 레시피가 바꾼다

**저장소와 pom의 환경 문제 (LLM 없이 처리)**
- [x] 저장소에 jar만 있고 pom이 없는 라이브러리: 한 저장소라도 pom 요청에 오류(예: Central 프록시의 502)로 답하면 Maven이 멈춘다. jar는 받을 수 있고 pom은 어디에도 없는지 확인한 뒤 파드의 로컬 저장소에 최소 pom을 만들고 같은 명령을 다시 실행한다(`build.pomless_stub`). 모든 Maven 호출에 적용, 플래그 `pomless-library`, 인수인계 한 줄, 그 pom으로 빌드한 다음 실행에도 알림 (v2.1z-ax)
- [x] 한글이 MS949 · EUC-KR 로 저장됐는데 XML 선언이 다른 pom: 취약점 조치가 Maven과 같은 기준으로 읽고 바이트를 보존하며 고친다. 정말 못 읽는 pom은 파일과 이유를 적어 거절한다 (v2.1z-ay)
- [x] 그런 pom은 자동 변환 전에 바로잡는다: 가능하면 선언만 `EUC-KR` 로, 아니면 UTF-8 로 다시 저장(`layout.legacy_context.correct_pom_encoding`). OpenRewrite가 읽지 못해 변환이 통째로 빠지던 문제 (v2.1z-ay)
- [x] 자동 변환이 실패하면 숨기지 않는다: 플래그 `rewrite-failed`, 인수인계 첫 줄, 결과 줄의 주의 코드. 프레임워크 프로젝트는 변환이 실패하면 빌드가 통과해도 성공이 아니다(`exit=2 build=ok`) (v2.1z-ay)
- [ ] 조치만 하는 실행이 최소 pom을 만들었을 때 보고서에 알리기(지금은 저널과 로그에만 남는다)

**사내 프레임워크 프로젝트**
- [x] 사내 프레임워크 아티팩트(`framework.artifacts`, 회사 yml)를 쓰는 프로젝트는 회사 레이아웃 · Boot 4 로 옮기지 않고 범위 `jdk-jakarta` 로 돈다: `framework.recipe_sets` 의 레시피(기본 Java 21 + jakarta), 레시피 전 MS949 · EUC-KR 소스 모듈의 `project.build.sourceEncoding` 쓰기(JDK 18부터 javac 기본이 UTF-8이고 OpenRewrite 도 못 읽는 파일은 건너뜀, 부모가 다른 값을 정하면 부모 값을 두고 인수인계), 레시피 뒤 as-is `provided` scope 되돌리기, JSP javax → jakarta, 빌드 1회, 빌드가 통과하든 실패하든 이어지는 취약점 조치. 재구성 · 구조 검토 · 빌드 오류 자동 수정 없음(LLM 0회), 부모 pom · 프레임워크 버전 유지, 결과 줄 `scope=jdk-jakarta` (v2.1z-ak, v2.1z-aw)
- [x] 찾는 곳: pom 의 직접 선언 → 부모 pom 에서 상속(as-is effective pom) → 트리 안 jar → 간접 의존성(`dependency:tree` 1회). 확인하지 못한 곳은 보고서와 저널에 남긴다
- [x] 빌드 오류는 고치지 않는다(`framework.fix_loop: false` 가 기본): 사전 시도 · 저장된 스크립트 · LLM 호출 없이 변환 뒤 남은 오류를 보고서에 적고 변환한 트리를 전달한다. 빌드 실패는 종료 코드 2. `true` 면 수정 루프로 고친다: 사전 시도(회사 부모 맞추기 없음) · 저장된 스크립트 · LLM (v2.1z-aw, v2.1z-bi)
- [x] 빌드가 실패한 프레임워크 프로젝트도 수정 루프를 돌았든 아니든 취약점 조치를 이어서 한다(`remediation.after_failed_build: framework`): 조치 전 빌드 실패를 받아들이고, 수정본 빌드가 조치 전과 같은 오류로만 실패하면 버전을 바꿔 다시 검사한다. 버전을 바꿨으면 빌드로 확인하지 못한 것이므로 완료가 아니라 `INCOMPLETE`(`baseline_build_failed`)로 끝나고, 바꾼 버전이 없으면 여느 조치처럼 끝난다. 일반 프로젝트와 조치만 하는 실행은 그대로 (v2.1z-aw)
- [x] 프레임워크 이름을 화면과 보고서에 쓴다: `framework.name`(회사 yml) 또는 아티팩트 이름에서 만든 이름(`example-fw-core` → `Example`). 올리기 카드 · 실행 카드 · 결과 카드와 보고서 첫 줄이 「<이름> 프레임워크는 JDK 21, Jakarta만 적용합니다.」 (v2.1z-aw)
- [x] `framework.fix_loop: true` 이면 수정 루프는 프레임워크 선언 · 버전과 `<parent>` 를 바꾼 시도를 되돌리고, javax 기준 프레임워크는 LLM 없이 담당자 몫으로 차단한다. 받지 못하는 부모 pom 은 어느 쪽이든 중단
- [x] 수정 루프를 켠 실행에서 프레임워크 검사를 끝내지 못한 시도는 받아들이지 않고 되돌린다(경고 한 줄, 예외 종류만). 읽지 못하거나 파싱되지 않는 pom 은 빌드에 맡긴다 (v2.1z-br)
- [ ] 실제 회사 프레임워크 프로젝트로 돌려 보기, 그 프로젝트의 이어지는 취약점 조치(실제 IVAS), Job 모드 화면

## 2. 빌드 오류 수정 루프와 지식베이스

- [x] 빌드 오류를 케이스(L2 서명)별로 묶고, 원인 쪽(pom · 의존성)부터 고치며 같은 파일을 건드린 케이스는 다음 빌드까지 기다린다
- [x] 사다리: 저장된 가장 좋은 스크립트 재사용(LLM 없음) → 이번 실행의 스크립트 보강(LLM) → 보강을 다 쓰면 새 스크립트(LLM)
- [x] 한도는 넉넉히: 케이스당 LLM 20회, 그중 보강 15회, 넘으면 BLOCKED `repeated_failure` (v2.1z)
- [x] 매 시도를 커밋하고 다시 빌드해 점수를 매긴다(좋아짐 · 일부 · 변화 없음 · 나빠짐 → 되돌림), 좋아지지 않은 시도는 다음 시도 전에 되돌린다
- [x] pom 수정이 다음 빌드 단계의 오류를 드러낸 것은 나빠진 것으로 치지 않는다 (v2.1z-z)
- [x] 루프가 끝날 때, 도움이 되지 않은 마지막 시도(변화 없음 · 판정 불가)는 최종 빌드 전에 되돌려 결과물에 남기지 않는다. 일부 좋아진 시도는 남긴다 (v2.1z-av)
- [x] 저장소가 응답하지 않아 받지 못한 것은 `repository_unreachable` 로 따로 분류한다: LLM 에 묻지 않고, 네트워크가 돌아와 통과한 빌드를 스크립트의 성과로 치지 않는다
- [x] 토큰 발급 실패는 LLM 장애로 다룬다(재시도 · 대기). 답이 토큰 한도에서 잘린 스크립트는 쓰지도 저장하지도 않고 짧게 다시 받는다

- [x] 고쳤으면 고친 바이트를 저장하고 상태를 저장한 뒤 수정본에 덮어쓰고, 확인 빌드 · 검증 · 확정을 거쳐 라운드마다 `rounds/<r>/fix.patch`, 모든 확정 라운드를 모은 `remediation/fix.patch`(내려받기 이름 `fix.patch`, cp949 소스도 UTF-8 로 보임)를 남기고, 보고서 「빌드 오류 수정」 절과 화면 칩 「소스 <n>개 수정」으로 알린다. 못 고쳤으면 수정본은 그대로이고 예전처럼 `candidate_build_failed` 로 끝나며 이유를 한 줄로 붙인다 (v2.1z-bi, v2.1z-bj, v2.1z-bk)

- [x] 수정본은 적용한 파일을 모두 저장했다는 증명(`rounds/<r>/applied/`, 경로마다 크기 · sha256 · 실행 비트를 담은 `rounds/<r>/expected.json`, 그 해시를 담은 `candidate.ready.json`)이 있을 때만 빌드한다. 없으면(적용 도중 종료, 이전 버전이 남긴 실행 폴더) `accepted/` 에서 다시 적용한다(저널 `candidate_rebuilt` 의 `why`) (v2.1z-bm)
- [x] 수정본 맞추기는 빌드할 때마다, 그리고 확정 직전과 실패한 수정본을 내보내기 직전에 한 번 더 한다. 저장한 표와 비교해 수정본 파일은 많아야 한 번 읽고 `accepted/` 는 다시 읽지 않는다. 모든 경로를 시도하고 읽기 전용 폴더 · 파일은 한 번 쓸 수 있게 한다. 그래도 되돌리지 못한 경로가 있으면 그 라운드는 확정도 전달도 하지 않고 `FAILED internal_error` 로 끝난다(앞 라운드의 검증된 결과 ZIP 은 남는다) (v2.1z-bm)
- [x] 중지 요청으로 멈춘 수정 루프는 재개하면 다시 돈다(`time budget used up` 은 그대로 최종). 도중에 끝난 루프의 LLM 사용량은 다음 빌드 노드(또는 보고서 노드)에서 무엇이 이어지든 한 번만 센다 (v2.1z-bm)
- [x] 고치지 못한 수정 루프의 보고서 문장은 「시도한 소스 수정은 결과에 넣지 않았습니다.」(수정본은 처음부터 건드리지 않았으므로 '되돌렸다'고 쓰지 않는다). 시도를 하나도 못 한 루프는 「빌드 오류 자동 수정을 하지 못했습니다(<사유>).」, 폴더를 준비하지 못한 루프는 시작하지 않은 것으로 적는다 (v2.1z-bm, v2.1z-bn)
- [x] 결과 ZIP은 모두 교체 한 번으로 쓴다: `delivery/.result.next.zip` 에 먼저 만들고 표식을 남긴 뒤 `result.zip` 을 바꾼다. 쓰지 못하면 앞 결과가 그대로 남고 `FAILED internal_error` 로 끝나며, 도중에 파드가 끝나면 다음 진입이 마무리하거나 되돌린다 (v2.1z-bn)
- [x] 보고서 노드 도중 끝난 끝 상태는 다음 진입(이어 돌기 · 재개 · 웹 파드)에서 보고서를 쓴다. 「결과 파일 — 없음」 문장은 끝난 까닭마다 맞게 쓴다. 빌드가 실행 비트만 바꾸거나 파일을 못 읽게 남겨도 되돌린다. 루프 밖으로 예외가 나와도 LLM 사용량은 루프 저널에서 읽고, 토큰을 모르는 호출에는 비용을 매기지 않는다 (v2.1z-bn)
- [x] 실제 Maven 시험(개발자 Mac, Maven 3.9.10 + JDK 21, 가짜 IVAS · 가짜 LLM): 일곱 실행이 모두 예상대로 끝났다. 이 시험이 산출물을 뺀 업로드의 검사 대상 문제를 찾았다 (v2.1z-bn)

- [x] 진행하던 쪽이 모두 끝났는데 보고서나 결과 ZIP 기록이 남은 끝 상태는 모든 모드에서 웹 파드가 한 번 맞춘다(상태 · 보고서 · 파일을 물을 때, 단독 조치는 시작 때). 상태 · 사유 · 메시지는 바꾸지 않는다 (v2.1z-bo)
