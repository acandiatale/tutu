sbmig · 지식 베이스(KB) kb-v2 · 지금 코드 기준

sbmig KB 데이터 지도

마이그레이션을 돌릴 때마다 kb-v2/ 폴더에 쌓이는 파일과 각 키의 뜻, 그리고 파일끼리 어떤 키로 이어지는지를 정리했습니다. 현업이 KB 데이터로 규칙을 만들 때 "이 값은 저 파일의 어느 키와 같다"를 찾는 용도입니다.

빌드 에러는 LLM이 쓴 파이썬 수정 스크립트(또는 LLM 이 직접 준 편집)로 고치고, 스크립트를 케이스(L2 시그니처)마다 버전으로 쌓습니다. 같은 케이스가 다음 프로젝트에 나오면 성적이 가장 좋은 버전을 LLM 없이 먼저 돌리고, 실패하면 그 버전을 LLM이 보강합니다. KB 는 오류 기록 한 파일 + 케이스 폴더뿐이고, 따라갈 키는 run_id · 오류 id · case_id(L2) · 스크립트 버전 네 개(+ 보강 계보 parent)입니다.

1. 폴더 구성 2. 연결 키 3. 데이터 흐름 4. 관계도 5. 시그니처 6. 상태 변화 7. 파일별 필드 사전 8. 값 목록 9. 자주 찾는 질문

1. 폴더 구성

원본 기록

  • errors.jsonl

모든 실행의 오류 한 건 = 한 줄. 실행이 끝날 때 그 실행의 오류 목록을 덧붙이고(이미 있는 id 는 건너뜀) 이미 쓴 줄은 고치지 않습니다. 나머지는 모두 이 파일에서 다시 만들 수 있습니다.

재사용 지식

  • cases/<case_id>/case.json
  • cases/<case_id>/fix_v<N>.py

다음 프로젝트에서 실제로 다시 실행되는 스크립트와 그 성적. 사람은 sbmig kb cases retire · activate · pin · unpin 으로만 손댑니다.

파생 사본

  • cases.md
  • cases/<case_id>/errors/*.json

사람이 읽는 표와 오류별 JSON. sbmig kb reindex 로 다시 만들 수 있으니 직접 고치지 않습니다. 회사가 채우는 libraries.yml · jar_names.yml 도 이 폴더에 둡니다(sbmig 는 읽기만).

운영 파일

  • .lock
  • 잠깐 생기는 .lock.breaker, .lock.probe.*, .fix.*.tmp

웹 파드·빌드 파드·플릿·sbmig kb 가 동시에 쓰지 않게 하는 잠금입니다.

kb-v2/
├── errors.jsonl                        오류 1건 = 1줄 (ErrorEntry: 시도·LLM 답·적용 diff·결과까지)
├── cases.md                            사람이 보는 케이스 표 (실행마다 다시 씀)
├── cases/<case_id>/
│   ├── case.json                       케이스 하나 = L2 하나 (CaseInfo: 스크립트 버전과 성적)
│   ├── fix_v1.py, fix_v2.py …          케이스별 수정 스크립트 (같은 코드는 한 번만 저장)
│   └── errors/<run_id>-<id>.json       오류 1건 = 파일 1개 (errors.jsonl 과 같은 내용, 들여쓰기)
├── cases/_other/errors/…               케이스 없는 항목 (pom-verify, 메모)
├── libraries.yml, jar_names.yml        사람이 채우는 표 (있을 때만)
└── .lock                               쓰기 잠금

kb-v2.bak-<시각>/                       kb import --replace 전에 남기는 이전 KB (kb-v2 옆)
<실행 폴더>/errors.jsonl, errors.md     그 실행의 오류 목록 (같은 레코드, md 는 사람용)

2. 파일을 잇는 연결 키

같은 값이 서로 다른 파일에 나타나므로 조인할 때 씁니다. 표에서 강조한 이름이 조인 키입니다.

키형식 / 만드는 법예시나오는 곳
run_id실행 한 번. run-YYYYMMDD-HHMMSS-<6자>run-20261031-193430-30da3derrors.jsonl 의 run_id, 오류별 JSON 파일 이름 앞부분, scripts[].created_by(만든 실행), scripts[].runs[].run_id(돌린 실행)
오류 idsha1(run_id | case_id | 파일 | 줄 | 메시지) 앞 12자. 같은 입력이면 같은 값3f1c9a0b7d2eerrors.jsonl 의 id, 오류별 JSON 파일 이름 끝, sbmig kb errors show <id>
case_id케이스 하나. sha1(L2) 앞 10자. L2 가 같으면 프로젝트가 달라도 같은 값. 케이스 폴더 이름도 이 값7a52b1cea8errors.jsonl 의 case_id, cases/<case_id>/, case.json 의 case_id, 커밋 메시지 fix(script:<case_id>:v<N> …), resolved_by[].case_id, 로그 [fix r3 <case_id>]
L2일반화한 시그니처 종류|분류|핵심 심볼 (경로·줄·버전·모듈 이름 없음). case_id 의 원문compile|package_does_not_exist|jakarta.xml.binderrors.jsonl 의 l2, case.json 의 l2
스크립트 버전케이스 안에서 1, 2, 3 … 같은 코드는 한 번만 저장, 번호는 다시 쓰지 않음. 0 = 스크립트 없음2파일 fix_v2.py, scripts[].version, tries[].script_version, errors.jsonl 의 script
parent보강의 원본 버전 번호. 새로 쓴 버전은 null1 (v2 는 v1 을 보강)scripts[].parent, scripts[].reason(원본이 왜 실패했나)
commit시도가 실행 폴더의 git 에 남긴 커밋a1b2c3dtries[].commit, resolved_by[].commit
project프로젝트 이름(루트 artifactId)legacy-shoperrors.jsonl 의 project, case.json 의 projects[], scripts[].projects[] / runs[].project

3. 데이터가 쌓이는 흐름

실행 한 번의 오류 목록이 KB 에 쌓이고, 그것을 고친 스크립트가 다음 프로젝트에서 다시 쓰이기까지의 경로입니다. 원통 모양이 kb-v2/ 안의 파일입니다.

flowchart LR
  subgraph RUN["실행 한 번 (sbmig run / 웹 / fleet)"]
    RS["구조 정리: pom 정정 → pom-verify 항목"] --> LIST["실행의 오류 목록"]
    RV["구조 검토 (LLM): 경고 → note 항목"] --> LIST
    BUILD["Maven 빌드 에러"] --> LIST
    LOOP["수정 루프: pre-try / 재사용 / 보강 / 신규"] -->|"시도 tries[]"| LIST
    LOOP -->|"LLM 스크립트 저장, 채점 뒤 성적"| SCR[("cases/case_id/fix_vN.py + case.json")]
  end
  LIST -->|"실행 끝: 덧붙임"| ERR[("errors.jsonl")]
  LIST -->|"사람용"| RUNMD["실행 폴더 errors.jsonl / errors.md"]
  ERR --> CJ[("case.json 수치 · cases.md · errors/*.json")]
  HUMAN["사람: kb cases retire / activate / pin"] --> SCR
  SCR -->|"같은 케이스: 가장 좋은 버전 재사용 (LLM 없음), 실패하면 보강의 바탕"| NEXT["다음 프로젝트의 수정 루프"]

한 케이스가 받는 시도는 아래 순서로 정해집니다(실행 한 번 안에서, 케이스마다). 자세한 규칙: agent-doc/04-cases-scripts-kb.md.

flowchart TD
  E["케이스 (L2 하나, 파일 여러 개)"] --> P{"LLM 없는 pre-try 가 맞나? (버전 채우기 · 바이너리 필터링 · jakarta 교체 · 동봉 jar)"}
  P -->|"예"| PT["source sbmig-version / -resources / -jakarta / -bundled"]
  P -->|"아니오"| Q1{"KB 에 이번 실행에서 아직 안 돌린 버전이 있나?"}
  Q1 -->|"있음"| R["재사용: proven 최신, 없으면 unverified 최신 · source kb-script"]
  Q1 -->|"없음"| Q2{"이번 실행의 직전 스크립트가 있고 보강이 남았나? (≤ 15)"}
  Q2 -->|"예"| A["보강: LLM 이 새 버전 작성 · parent = 바탕 · llm-augment"]
  Q2 -->|"아니오"| N["신규: LLM 이 새로 작성 · llm-new (코드로 안 되면 edits 만: llm-edit)"]
  PT --> S["다시 빌드 · 채점 · 성적 기록"]
  R --> S
  A --> S
  N --> S
  S -->|"케이스 오류가 모두 사라짐"| OK["resolved · 버전 성공 +1"]
  S -->|"일부만 / 그대로 / 악화"| RB["되돌림 (git), 다시 사다리로"]
  RB --> Q1
  S -->|"LLM 요청 20회 소진 또는 거절"| BLK["blocked → Handover"]

5. 시그니처: 에러 하나가 케이스 키가 되는 과정

flowchart LR
  LOG["Maven 로그 한 줄"] --> BE["BuildError: 종류 · 파일 · 줄 · 메시지 · 심볼"]
  BE --> L1["L1 (구체): 정규화 메시지 + 심볼 + 위치"]
  BE --> L2["L2 (일반): 종류|분류|핵심 심볼 — 경로·줄·버전·모듈 이름 없음"]
  L2 --> REF["포괄 키(build / other)는 원문 첫 줄로 세분"]
  REF --> CID["case_id = sha1(L2) 앞 10자"]
  CID --> DIR["cases/case_id/ — 다음 프로젝트에서 같은 폴더를 찾음"]
  • 리액터 모듈의 artifactId 는 <module> 로 가립니다. 그래서 프로젝트가 달라도 같은 원인은 같은 케이스입니다.
  • L2 가 없는 오류는 sha1(종류|파일|L1) 앞 10자를 씁니다.
  • 시그니처 규칙(sbmig/build/signatures.py)이 바뀌면 옛 규칙으로 저장된 케이스와는 매칭이 끊깁니다(알려진 과제, agent-doc/10-open-items-and-history.md).

6. 상태 변화

오류 항목 (errors.jsonl 의 status)

stateDiagram-v2
  state "pom-verify" as pom_verify
  state "note" as note_entry
  [*] --> open : 빌드에서 처음 봄
  [*] --> pom_verify : 구조 정리가 고친 pom
  [*] --> note_entry : 구조 검토 경고 · 안내
  open --> resolved : 시도로 사라짐 / 빌드에서 사라짐
  pom_verify --> resolved : 다음 빌드가 확인
  open --> blocked : 한도 소진 · 거절 · 외부 원인
  open --> unresolved : 실행이 끝날 때 남음

스크립트 버전 (scripts[].status)

stateDiagram-v2
  [*] --> unverified : 저장
  unverified --> proven : 만든 프로젝트가 아닌 곳에서 재사용으로 해결
  unverified --> retired : 사람 (kb cases retire) · 비밀값이 들어 있던 스크립트
  proven --> retired : 사람
  retired --> unverified : kb cases activate (다른 곳에서 해결한 적 없으면)
  retired --> proven : kb cases activate (해결한 적 있으면)

재사용 순서: proven 최신 → unverified 최신. retired 와 non_idempotent(두 번 돌렸더니 또 바뀐 스크립트)는 고르지 않습니다.

7. 파일별 필드 사전

errors.jsonl원본 기록오류 1건 = 1줄 (ErrorEntry) — 실행 폴더의 errors.jsonl 과 같은 레코드
필드뜻
id오류 id (2절)
run_id, project실행, 프로젝트 이름
case_id, l2케이스 (2절)
kind오류 종류 (8절)
file, line, module위치 (프로젝트 기준 상대 경로)
message, raw메시지, 로그 원문(최대 600자)
seen처음 본 곳: restructure · review · build · fix r3 (compile 은 변환 뒤 컴파일을 켰을 때만)
status8절
tries[]이 오류의 케이스에 들어간 시도 (아래 표)
resolved해결한 곳: r3 try 2(그 시도) · build(자기 시도 없이 사라짐) · review
resolved_by[]resolved: build 일 때 같은 라운드에 그 파일이나 모듈 pom 을 바꾼 시도: case_id, round, n, commit, files, match(file · pom · reindex), text
script해결한 스크립트 파일 cases/<case_id>/fix_v<N>.py
notepom-verify: 구조 정리가 한 일 / note 항목: 그 글
at기록 시각 (UTC)
tries[]원본 기록시도 1건 (FixTry)
필드뜻
n, round케이스 안 시도 번호, 수정 루프 라운드(0 = 구조 검토)
source사다리 단계 (8절)
script_version돌리거나 만든 스크립트 버전 (0 = 없음)
analysis, solutionLLM 의 원인 / 해결 방법
no_script_reason스크립트로 안 되는 이유 (LLM 이 편집만 준 경우)
applied실제로 적용된 것: script · edits · none
files, edits[]바뀐 파일, 수정 내역(path, where, change, lines, source(llm · diff), hunks[] = 수정 전 before / 수정 후 after)
major_upgrades[], verify, verify_source이 시도가 pom 에서 올린 메이저 버전 / 바꾼 라이브러리, 운영자 확인 안내와 누가 썼는지
diff, commit적용한 diff, git 커밋
result, note재빌드 채점 결과 (8절), 실패 이유·되돌림 메모
llm_calls, seconds이 시도의 LLM 호출 수, 걸린 초
cases/<case_id>/case.json재사용 지식케이스 하나 (CaseInfo)
필드뜻
case_id, l2, name, kind케이스 키, 사람이 읽는 이름(예: package jakarta.xml.bind does not exist), 종류
projects[]이 케이스를 본 프로젝트
seen, resolved모든 실행의 오류 수, 해결 수
scripts[]저장된 스크립트 버전 (아래 표)
last_analysis, last_solution마지막 LLM 원인 / 해결
updated_at마지막 갱신
pin(모델 밖 키) 사람이 고정한 차단 block[:이유] — 이 케이스는 시도하지 않음
last_result(모델 밖 키) 마지막 결과
scripts[]재사용 지식스크립트 버전 (CaseScript) — 파일은 같은 폴더의 fix_v<N>.py
필드뜻
version, file버전 번호, 파일 fix_v<N>.py
statusunverified · proven · retired (6절)

9. 자주 찾는 질문과 따라갈 키

이 오류는 어떻게 고쳤나?

  1. sbmig kb errors show <오류 id>
  2. resolved 가 r3 try 2 면 tries[] 의 그 시도(analysis, edits[].hunks, diff)
  3. build 면 resolved_by[]

무엇을 시도했다가 왜 실패했나?

  1. 같은 항목의 tries[] 에서 result 가 실패인 것의 note
  2. 스크립트라면 case.json 의 scripts[].runs[].reason

이 스크립트는 어디서 왔고 무엇을 보강했나?

  1. sbmig kb cases show <case_id>
  2. scripts[] 의 parent · reason · created_by

다음 프로젝트에서 이 케이스는 무엇을 실행하나?

  1. proven 최신, 없으면 unverified 최신
  2. kb cases show 의 KB 탐색: 줄

같은 원인이 몇 프로젝트에서 나왔나?

  1. case.json 의 projects[]
  2. cases.md

스크립트나 케이스를 막으려면?

  1. 나쁜 버전: sbmig kb cases retire <case_id> <N> (되돌리기 activate)
  2. 케이스 전체: sbmig kb cases pin <case_id> block:<이유> (풀기 unpin)

주의할 점

  1. cases.md 와 errors/*.json 은 파생 사본이라 직접 고치지 말 것 (kb reindex 로 다시 만듦)
  2. KB 를 다른 PC 로 옮길 때는 sbmig kb export / import
