sbmig KB 데이터 지도

마이그레이션을 돌릴 때마다 kb-v2/ 폴더에 쌓이는 파일과 각 키의 뜻, 그리고 파일끼리 어떤 키로 이어지는지를 정리했습니다. 현업이 KB 데이터로 규칙을 만들 때 "이 값은 저 파일의 어느 키와 같다"를 찾는 용도입니다.

v2 흐름(브랜치 flow-v2): 빌드 에러는 모두 LLM이 쓴 파이썬 수정 스크립트로 고치고, 스크립트를 케이스(L2 시그니처)마다 버전으로 쌓습니다. 같은 케이스가 다음 프로젝트에 나오면 성적이 가장 좋은 버전을 LLM 없이 먼저 돌리고, 실패하면 그 버전을 LLM이 보강합니다. 그래서 KB는 에러 · 시도 · 구조 점검 기록, 케이스, 스크립트로 줄었고, 현업이 따라갈 연결 키는 run_id · 에러 id · 시도 id · case_id(L2) · 스크립트 버전 다섯 개(+ 보강 계보 parent)입니다. v1(태그 company-v1)의 kb/ 폴더와는 섞지 않습니다. v1에서만 쓰던 파일은 1절 끝 상자에 모았습니다.

1. 네 가지 층 2. 연결 키 3. 데이터 흐름 4. 관계도 ① 실행 기록 5. 관계도 ② 케이스와 스크립트 6. 시그니처 계층 7. 상태 변화 8. 파일별 필드 사전 9. 값 목록 10. 자주 찾는 질문

1. KB는 네 가지 층으로 나뉩니다

사실 기록

  • errors.jsonl
  • fix_attempts.jsonl
  • reviews.jsonl 구조 점검 (v2 새로)

실행할 때마다 줄이 추가되고 이미 쓴 줄은 고치지 않습니다. 규칙을 만들 때 근거로 쓰는 원본 데이터입니다.

재사용 지식

  • catalog/ 에러 케이스
  • scripts/ 케이스별 수정 스크립트와 성적 (v2 새로)

다음 프로젝트에서 실제로 다시 실행되는 지식입니다. 사람은 케이스 파일의 human: 블록과 sbmig kb scripts retire · activate 명령으로만 손댑니다.

파생 인덱스

  • catalog/index.json
  • views/ 사람이 보는 표

위 두 층에서 계산한 검색용 사본입니다. sbmig kb reindex로 언제든 다시 만들 수 있으니 직접 고치지 않습니다.

운영 파일

  • audit.jsonl 변경 이력 (스크립트 포함)
  • quarantine.jsonl 읽지 못한 줄
  • *.jsonl.corrupt, .lock

누가 언제 무엇을 바꿨는지, 깨진 줄은 무엇인지 남깁니다. 동시에 쓰지 않도록 잠금 파일도 둡니다.

3. 데이터가 쌓이는 흐름

7. 상태 변화: 케이스와 스크립트 버전

케이스 (catalog/*.yml의 status)

stateDiagram-v2
  [*] --> observed : 처음 본 에러
  observed --> candidate : 이 케이스의 스크립트 버전이 성공
  candidate --> active : 그 버전이 서로 다른 프로젝트 2곳 성공, 실패 없음
  active --> candidate : 그 버전이 실패
  candidate --> observed : 검증된 버전이 없어짐 (사람이 retire)
  observed --> rejected : 사람이 reject
  candidate --> rejected : 사람이 reject
  active --> rejected : 사람이 reject

사람이 human: 블록의 status나 action을 정하면 자동 값보다 우선합니다(sbmig kb cases pin <id> --action script:N). 상태가 바뀔 때마다 audit.jsonl에 한 줄이 남습니다. 승격 기준 프로젝트 수는 설정 kb.auto_promote_after_projects(기본 2)입니다.

스크립트 버전 (v<N>.meta.json의 status)

stateDiagram-v2
  [*] --> active : LLM이 쓴 스크립트를 실행 전에 저장
  [*] --> quarantined : 코드에 비밀값 → 가려서 저장
  active --> retired : 사람이 kb scripts retire
  retired --> active : 사람이 kb scripts activate

재사용 후보 = active이고 성공이 1번 이상인 버전. 순서: 고친 프로젝트 수 → 성공 − 실패 → 최신 버전. 사람이 고정한 버전은 active이면 맨 앞(성공이 없어도). retire가 고정보다 우선하고, quarantined는 절대 선택되지 않으며, 사람이 reject한 케이스는 재사용하지 않습니다. 보강의 바탕(latest)은 가장 최근의 active 버전입니다.

10. 자주 찾는 질문과 따라갈 키

이 에러는 어떻게 고쳤나?

  1. errors.jsonl에서 status = resolved인 줄
  2. script_case_id + script_version → scripts/<case_id>/v<N>.py (실행한 코드)
  3. resolved_by와 같은 id의 fix_attempts.jsonl 줄 → diff, script_log
  4. 명령으로 한 번에: sbmig kb errors show <에러 id>

무엇을 시도했다가 왜 실패했나?

  1. errors.jsonl의 attempts[]: fix_method, script_version, outcome, failure
  2. 같은 attempt_id의 fix_attempts.jsonl: script_status, script_error, script_log, introduced_errors
  3. sbmig kb errors show <id> --all-diffs

이 스크립트는 어디서 왔고 무엇을 보강했나?

  1. scripts/<case_id>/v<N>.meta.json의 run_id, project, model, analysis
  2. parent를 따라가면 보강 계보 (v1 → v2 → v4)
  3. sbmig kb scripts show <case_id> --version N

다음 프로젝트에서 이 케이스는 무엇을 실행하나?

  1. 케이스 파일의 action.script_version (사람이 고정했으면 human.action)
  2. views/cases.csv의 best_script
  3. sbmig kb scripts list --case <case_id>

같은 원인이 몇 프로젝트에서 나왔나?

  1. errors.jsonl을 case_id로 묶고 project_fingerprint를 셈
  2. 또는 케이스 파일의 evidence.projects
  3. 스크립트가 고친 프로젝트: meta의 success_projects

구조 점검은 무엇을 지적했나?

  1. reviews.jsonl에서 run_id가 같은 줄
  2. issues[]의 severity, problem, fix_hint
  3. 고쳤다면 commit과 script_result.changed_files

사람이 무엇을 바꿨나?

  1. audit.jsonl에서 event = human, 또는 event = script이고 action = retired / activated
  2. case_id → 케이스 파일의 human: 블록
  3. sbmig kb cases show <case_id> (history 구역)

엑셀로 보고 싶다

  1. 실행 폴더의 error_cases.csv (UTF-8 BOM, 열 = errors.jsonl 필드, raw 앞에 script_case_id, script_version)
  2. KB 전체: sbmig kb errors export --csv e.csv --attempts-csv a.csv (시도 CSV는 diff_truncated 앞에 script_* 7열)
  3. 케이스 표: views/cases.csv (끝에 scripts, best_script)

주의할 점

  1. v2 KB는 kb-v2/. v1 kb/와 섞지 말 것 (형식이 다름, schema_version 3)
  2. script_version 0 = 저장되지 않은 스크립트 (KB 없이 돌린 실행)
  3. success_projects는 프로젝트 이름, project_fingerprint는 해시로 서로 다름
  4. 파생 인덱스는 직접 고치지 말 것 (kb reindex로 다시 만듦)
