sbmig KB 데이터 지도

마이그레이션을 돌릴 때마다 kb/ 폴더에 쌓이는 파일과 각 키의 뜻, 그리고 파일끼리 어떤 키로 이어지는지를 정리했습니다. 현업이 KB 데이터로 규칙을 만들 때 "이 값은 저 파일의 어느 키와 같다"를 찾는 용도입니다.

1. 네 가지 층 2. 연결 키 3. 데이터 흐름 4. 관계도 ① 실행 기록 5. 관계도 ② 재사용 지식 6. 시그니처 계층 7. 상태 변화 8. 파일별 필드 사전 9. 값 목록 10. 자주 찾는 질문

1. KB는 네 가지 층으로 나뉩니다

사실 기록

  • errors.jsonl
  • fix_attempts.jsonl
  • ledger.jsonl

실행할 때마다 줄이 추가되고 이미 쓴 줄은 고치지 않습니다. 규칙을 만들 때 근거로 쓰는 원본 데이터입니다.

재사용 지식

  • catalog/ 에러 케이스
  • recipes/ OpenRewrite 레시피
  • cases/ 재생용 패치
  • patterns/ 사람이 쓴 규칙

다음 프로젝트에서 실제로 적용되는 지식입니다. 사람은 케이스 파일의 human: 블록만 고칩니다.

파생 인덱스

  • index.json
  • symbols.json
  • error_hints.json
  • catalog/index.json, views/

위 두 층에서 계산한 검색용 사본입니다. sbmig kb reindex로 언제든 다시 만들 수 있으니 직접 고치지 않습니다.

운영 파일

  • audit.jsonl 변경 이력
  • quarantine.jsonl 읽지 못한 줄
  • *.jsonl.corrupt, .lock

누가 언제 무엇을 바꿨는지, 깨진 줄은 무엇인지 남깁니다. 동시에 쓰지 않도록 잠금 파일도 둡니다.

kb/
├── errors.jsonl                         빌드 에러 1건 = 1줄 (ErrorCaseRecord)
├── fix_attempts.jsonl                   수정 시도 1건 = 1줄, 실패 포함, 적용한 diff (FixAttemptRecord)
├── ledger.jsonl                         에러 묶음(클러스터) 1건의 해결 방법 = 1줄 (ResolutionRecord)
├── catalog/<종류>/<분류>/<심볼>--<case_id>.yml  L2 시그니처 1개 = 케이스 1개 (CatalogCase)
├── recipes/candidates|active|rejected/<레시피 id>.yml + .meta.json  (KBRecipe)
├── cases/YYYY-MM/<KB 케이스 id>.json      재생할 수 있는 LLM 패치 (KBCase)
├── patterns/*.yml                       사람이 쓴 매칭 규칙 (항상 켜짐)
├── index.json                           시그니처 → KB 케이스 / 레시피
├── symbols.json                         에러 심볼 → 고친 방법 묶음
├── error_hints.json                     L2 / 에러 심볼 → 과거 성공·실패 (LLM 프롬프트 힌트)
├── catalog/index.json                   케이스 id → 파일, L2 / L1 / 심볼 → 케이스 id
├── views/cases.md, cases.csv            사람이 보는 케이스 표
├── audit.jsonl                          사람의 케이스 수정 + 자동 상태 변화
├── quarantine.jsonl                     errors.jsonl에서 읽지 못한 줄의 메모
├── *.jsonl.corrupt                      중간에 끊겨 반쯤 쓰인 마지막 줄을 옮겨 둔 곳
└── .lock                                여러 프로세스가 동시에 쓰지 않게 하는 잠금

kb.bak-<시각>/                            kb import --replace 전에 남기는 이전 KB 백업 (kb 폴더 옆)
<실행 폴더>/error_cases.jsonl, fix_attempts.jsonl, error_cases.csv   그 실행분만 따로 (같은 형식, CSV는 엑셀용)

2. 파일을 잇는 연결 키

3. 데이터가 쌓이는 흐름

빌드 에러 하나가 기록되고, 고친 방법이 다음 프로젝트에서 다시 쓰이기까지의 경로입니다. 원통 모양이 kb/ 안의 파일입니다.

flowchart LR

    BUILD["Maven 빌드 에러"] --> TRACK["에러 추적기"]
    LOOP["수정 루프 시도 (핸들러 / 레시피 / 패치 재생 / LLM)"] --> TRACK

  TRACK -->|"시도마다 1줄 + diff"| ATT[("fix_attempts.jsonl")]

  LOOP -->|"성공한 LLM 수정"| HV["harvest"]
  HV --> KC[("cases/ 재생용 패치")]
  KC -->|"라벨로 컴파일 (LLM 없음)"| RC[("recipes/candidates")]
  RC -->|"서로 다른 프로젝트 2곳 성공"| RA[("recipes/active")]

4. 관계도 ① 실행 기록: 에러 · 시도 · 케이스

한 실행에서 생긴 에러와 시도, 그리고 그것들을 L2 기준으로 모은 케이스의 관계입니다. 선의 글자가 연결에 쓰이는 키입니다.

5. 관계도 ② 재사용 지식: 패치 · 레시피 · 인덱스

다음 프로젝트에서 실제로 적용되는 지식과, 그것을 빨리 찾기 위한 인덱스의 관계입니다. 케이스의 action이 레시피나 패치를 가리키면, 케이스가 적중했을 때 그것이 적용됩니다.

그림 ①과 ②에 kb/의 모든 기록 파일이 들어 있습니다. 키로 다른 파일과 이어지지 않는 운영 파일 .lock(쓰기 잠금), *.jsonl.corrupt(반쯤 쓰인 줄), kb.bak-<시각>/(kb import --replace 전 백업)만 그림에서 뺐습니다. 실행 폴더(out/<run id>/의 journal.jsonl, report.json, plan.json, changes.patch 등)와 플릿 폴더(state.json, summary.*)는 KB가 아니라 이 지도에 넣지 않았습니다. 다만 실행 폴더의 error_cases.jsonl, fix_attempts.jsonl, error_cases.csv는 KB의 같은 이름 파일과 형식이 같습니다.

6. 시그니처 계층: 에러 하나가 여러 키가 되는 과정

같은 에러가 어느 정도로 "같은지"에 따라 키가 셋입니다. 케이스를 찾을 때는 L1 → L2 → 에러 심볼 순서로 맞춰 봅니다.

flowchart TD
  RAW["Maven 에러 원문 (raw)"] --> L1["L1 signature: 종류 | 분류 | 심볼 전체 | 소유 클래스"]
  L1 --> L2["L2 signature_generic: 종류 | 분류 | 핵심 심볼"]
  L2 --> CID["case_id = sha1(L2) 앞 10자"]

7. 상태 변화: 케이스와 레시피

케이스 (catalog/*.yml의 status)

stateDiagram-v2
  [*] --> observed : 처음 본 에러
  observed --> candidate : 다시 쓸 수정이 생김
  candidate --> active : 서로 다른 프로젝트 2곳 성공, 실패 없음
  candidate --> observed : 치환 실패가 2회 이상이고 성공보다 많음
  observed --> rejected : 사람이 reject
  candidate --> rejected : 사람이 reject
  active --> rejected : 사람이 reject

사람이 human: 블록의 status나 action을 정하면 자동 값보다 우선합니다. 상태가 바뀔 때마다 audit.jsonl에 한 줄이 남습니다.

레시피 (recipes/ 폴더)

stateDiagram-v2
  [*] --> candidates : 성공한 LLM 수정의 라벨로 컴파일, 또는 레시피 모델이 작성
  candidates --> active : 서로 다른 프로젝트 2곳 성공
  candidates --> rejected : 사람이 kb reject
  active --> rejected : 사람이 kb reject

승격 기준 프로젝트 수는 설정 kb.auto_promote_after_projects(기본 2)입니다. 성공·실패 횟수는 레시피의 .meta.json에 쌓입니다.

10. 자주 찾는 질문과 따라갈 키

이 에러는 어떻게 고쳤나?

  1. errors.jsonl에서 status = resolved인 줄
  2. resolution_attempts[]의 시도 id들
  3. 같은 id의 fix_attempts.jsonl 줄 → diff
  4. 명령으로 한 번에: sbmig kb errors show <에러 id>

무엇을 시도했다가 왜 실패했나?

  1. errors.jsonl의 attempts[]: outcome, failure
  2. 실패한 시도의 코드: 같은 attempt_id의 fix_attempts.diff
  3. sbmig kb errors show <id> --all-diffs

같은 원인이 몇 프로젝트에서 나왔나?

  1. errors.jsonl을 case_id로 묶고 project_fingerprint를 셈
  2. 또는 케이스 파일의 evidence.projects
  3. 더 넓게: error_symbol로 묶기

규칙으로 바꿀 후보는? (LLM이 단순 치환으로 고친 것)

  1. errors.jsonl에서 replace_rule_candidate = true
  2. replace_pairs와 case_id로 묶기
  3. sbmig kb errors replace-candidates

이 레시피는 어디서 나왔나?

  1. recipes/…/<id>.meta.json의 source_case_ids
  2. cases/…/<KB 케이스 id>.json의 tags attempt:<attempt_id> + project
  3. 그 실행의 fix_attempts.jsonl에서 diff

사람이 무엇을 바꿨나?

  1. audit.jsonl에서 event = human
  2. case_id → 케이스 파일의 human: 블록
  3. sbmig kb cases show <case_id> (history 구역)

엑셀로 보고 싶다

  1. 실행 폴더의 error_cases.csv (UTF-8 BOM, 열 = errors.jsonl 필드)
  2. KB 전체: sbmig kb errors export --csv e.csv --attempts-csv a.csv (--case, --resolver 필터)
  3. 케이스 표: views/cases.csv

주의할 점

  1. ledger.case_id는 KB 케이스 id(2026…-…), errors.case_id는 카탈로그 케이스 id(10자)로 서로 다름
  2. 파생 인덱스는 직접 고치지 말 것 (kb reindex로 다시 만듦)
  3. KB 형식이 바뀌면 schema_version이 올라감
